GameGo studies **how to formulate and collect training tasks for agents that build playable browser games**. Starting from real-world game seeds, it makes mechanics, interaction flows, camera behavior, and asset requirements explicit in a structured product requirements document (PRD). A task-adaptive query then carries the essential constraints into a coding-agent rollout. The resulting development trajectories and runnable artifacts form **GameGoData**, which is used to train **GameGoCoder**.

> **Explore the result:** [open the interactive game gallery](https://haoyue-yang.github.io/GameGo/games/) and play 12 games generated by GameGoCoder 3.8 in your browser.

**Research question.** Short game requests often omit the rules and dependencies needed to produce a complete game. Full specifications resolve many ambiguities but can overload a coding agent. GameGo investigates a middle ground: construct a comprehensive internal specification, then deliver a compact query whose detail matches the task's complexity.


## Method: expand, then project

```text
Real-world game seeds
        ↓
Task definition → playable blueprint → asset grounding
        ↓
Complete PRD
        ↓  task-adaptive query construction
Compact execution query
        ↓
Coding-agent rollout in a browser-game sandbox
        ↓
Verified development trajectory + runnable artifact
        ↓
GameGoData → supervised fine-tuning → GameGoCoder
```

1. **Specify the game.** Staged planning converts a seed into a task definition, a closed playable loop, and an asset plan. These are compiled into a PRD that captures cross-cutting requirements such as controls, state transitions, spatial relationships, and visual realization.
2. **Construct the execution query.** Task-adaptive compression retains gameplay-defining constraints while removing redundant detail. The resulting query gives the coding agent enough structure to build the intended game without prescribing every implementation choice.
3. **Collect process supervision.** A coding agent builds each game in a sandbox. Development messages, tool interactions, and the final artifact are retained after execution, artifact-integrity, and format checks.

The [pipeline figure](./figure/mainpic.pdf) gives a more detailed view of the task-construction and trajectory-collection process.

## Data and evaluation

**GameGoData** contains 55,060 filtered trajectories spanning 2D (61.4%), 2.5D (20.1%), and 3D (18.5%) browser games across 20 gameplay categories. Each retained example pairs a development process with a runnable game artifact.

**GameGoBench** contains 124 held-out tasks: 47 in 2D, 22 in 2.5D, and 55 in 3D. Tasks are stratified by difficulty, and benchmark seeds are separated from training seeds before task construction. Evaluation considers browser execution, requirement satisfaction, and visual and interaction quality.

## Results

On GameGoBench, both GameGoCoder models improve over their matched base models. Scores below are the values reported in the GameGo manuscript; **Overall** is the benchmark's aggregate score.

| Model | Execution | Requirements | Quality | Overall |
| --- | ---: | ---: | ---: | ---: |
| Qwen3.5-27B | 91.80 | 36.89 | 31.12 | 34.00 |
| **GameGoCoder 3.5** | **98.29** | **57.99** | **45.72** | **51.85** |
| Qwen3.8-27B | 100.00 | 62.81 | 42.25 | 52.53 |
| **GameGoCoder 3.8** | **100.00** | **66.94** | **43.64** | **55.29** |

GameGoCoder 3.5 gains **17.85** Overall points over Qwen3.5-27B; GameGoCoder 3.8 gains **2.76** points over Qwen3.8-27B. In the task-representation study, task-adaptive queries achieve a median **3.79× relation-density gain** over full PRDs. Blinded human judgments report **85.7%** preference for games generated from these queries over games generated from full PRDs, and **86.6%** over games generated from direct queries.
